**Grant reality (gap 1).** Postgres denies access to a newly created table by default. The 5
new content tables will be inaccessible to `szronox_api`/`szronox_worker` the instant
`migrate` creates them, until `grants.sql` runs again. The branch's `grants.sql`
(`deploy/vps/postgres/grants.sql`) already grants exactly `SELECT` on all 8 corpus content
tables and — critically — **never mentions** `programme_proposal_enrichment_revisions`, so
that audit table stays deny-by-default to both runtime roles with zero grant statement
required. That is the correct, and safest possible, posture: not writable *and not readable*
by either running service.

**Storage reality (gap 2).** A one-off container must attach the volume by name
(`-v szronox-dev_app_storage:/var/lib/szronox/storage`), never a host directory that merely
shares the pathname — there is no such host directory. `storage-init` creates
`staging`/`objects` under the volume, owned `1000:1000` mode `700`, but not `programme/`;
`stageArchiveFile` (`apps/api/src/ai/corpus/archive.ts:60`) creates it itself
(`mkdir(..., { recursive: true })`), and the image's default user is `node` (uid 1000,
`deploy/vps/Dockerfile:14`) — matching the volume's ownership, so no extra pre-step is needed.

### 3.1 Backup

Two independent backups, plus a fresh named export of the **current** release (`d3c5910`) —
there is currently no `app.d3c5910/` on the host the way there is `app.402193c`/`app.758d780`/
`app.a248baf`, so without this step a code rollback to the release running right now would have
no target to restore from.

```bash
BACKUP=pre-corpus-$(date -u +%Y%m%dT%H%M%SZ)
sudo install -d -m 0755 /opt/szronox-dev/backups/$BACKUP
cd /opt/szronox-dev

# 1. Snapshot the currently live release directory (not yet backed up under its own name).
sudo cp -a app app.d3c5910

# 2. Database dump (custom format), same mechanism as the established pre-gemini-02 backup.
docker exec szronox-dev-postgres-1 sh -c \
  'PGPASSWORD=$(cat /run/secrets/postgres_password) pg_dump -U szronox_dev -d szronox_dev -F c' \
  > backups/$BACKUP/szronox_dev.dump

# 3. Private storage volume, via the named volume (never a host path).
docker run --rm -v szronox-dev_app_storage:/data -v "$PWD/backups/$BACKUP:/backup" alpine:3.20 \
  sh -c 'tar czf /backup/app_storage.tar.gz -C /data .'

# 4. State-before-the-fact, for the rollback doc.
docker exec szronox-dev-postgres-1 psql -U szronox_dev -d szronox_dev \
  -c 'select name, applied_at from public.schema_migrations order by name;' \
  > backups/$BACKUP/schema_migrations.before.txt
docker ps --format '{{.Names}}\t{{.Image}}\t{{.Status}}' | sort > backups/$BACKUP/containers.before.txt
echo "d3c5910" > backups/$BACKUP/release.before.txt
```

Verify before proceeding: `ls -la backups/$BACKUP/` shows all four files non-empty;
`gunzip -t backups/$BACKUP/app_storage.tar.gz` (or re-`tar tzf`) succeeds.

### Corpus (data) rollback

- **If activation already happened and needs to be undone while keeping the code deployed**:
  there is no "deactivate to empty" command by design (`docs/product/programme-corpus-spec.md`
  requires exactly one active release whenever the corpus is meant to be searchable at all).
  The corrective action is a direct, reviewed `UPDATE app.programme_releases SET
  state='withdrawn', withdrawn_at=now() WHERE release_slug='zieloni-programme-2026-draft-r1'`
  by the schema owner, outside the CLI — restated from `CORPUS-03-result.md` §8, not a new
  decision made here.
- **First-release case (this deployment)**: since `activate`'s own output already confirmed "No
  previous release existed for this corpus" (§3.6), there is nothing to restore *to* — the
  correct undo for "this release should not have been active" is the `withdrawn` update above,
  which leaves the corpus with zero active releases (matching its state before this
  deployment), not a restore of some other release.
- **Full data restore** (only if the import/activation itself corrupted something, not for an
  ordinary "wrong content" correction — prefer `withdrawn` + a corrected re-import first):
  ```bash
  docker exec -i szronox-dev-postgres-1 sh -c \
    'PGPASSWORD=$(cat /run/secrets/postgres_password) pg_restore -U szronox_dev -d szronox_dev --clean --if-exists' \
    < /opt/szronox-dev/backups/$BACKUP/szronox_dev.dump
  docker run --rm -v szronox-dev_app_storage:/data -v /opt/szronox-dev/backups/$BACKUP:/backup alpine:3.20 \
    sh -c 'rm -rf /data/* && tar xzf /backup/app_storage.tar.gz -C /data'
  ```
